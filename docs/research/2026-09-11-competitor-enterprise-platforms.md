## Factory AI — Droid + Software Factory

**What it is / status (2026-09)**: Enterprise agent platform: Droid CLI + Factory App + Droid SDK. New in 2026: **Software Factory** — a 24/7 autonomous SDLC system covering intake→triage→code-gen→validate→release→document→monitor, in **Private Preview** (docs.factory.ai/software-factory/overview). Factory is no longer "an agent"; it claims DevAgent's exact framing: "connects AI agents across the software development lifecycle".

**Trigger surfaces**
- Slack messages (channels/keywords/message-source), GitHub events (PR opened/synchronize/reopened/ready_for_review, pushes, comments, labels, checks), natural-language/cron schedules, Linear ("Open in Factory" attachment), `/droid` PR comments via `Factory-AI/droid-action`, REST API (`/api-reference/automations-ci`).
- An Automation = {trigger, prompt, run target (service account + Droid Computer + working directory + model), visibility private/shared}, with run history and pause/resume/fork. Shared automations run under **service accounts** — identity is the automation, not a human (software-factory/automations).

**Workflow pipeline (stage by stage)**
1. **Spec gate before mutation.** **Spec Mode** default: read-only planning → structured plan; approval is an explicit `ExitSpecMode` tool call; then Autonomy Level Off/Low/Medium/High governs unprompted actions (org `maxAutonomyLevel` caps it). Approved plans persist as `.factory/docs/YYYY-MM-DD-slug.md` (specification-mode).
2. **Headless one-shot** (`droid exec`): default read-only; `--auto <level>` opts into mutations; exit 0/non-zero is the CI gate ("unmet objective" fails). Tool allowlists (`--restrict-tools`), session fork (`--fork`), tags + `--log-group-id`, JSON-RPC streaming, `--append-system-prompt[-file]` per-run policy injection (droid-exec/overview).
3. **Mission planning**: `/missions` conversational plan (features, milestones, skills, validation strategy); "the biggest value in Missions is in the planning phase"; 1–500 features sweet spot (missions/overview).
4. **Feature workers**: ~1 run per feature; **validation workers**: ~2 per milestone; published cost heuristic `total runs ≈ #features + 2 × #milestones` (missions/planning).
5. **Two validation worker kinds per milestone** — **scrutiny** and **user-testing** — each with own model/reasoning settings (`missionModelSettings.validationWorkerModel`, `skipScrutiny`, `skipUserTesting`); a "feature retry limit" warning fires on repeated feature failure (missions/reference).

**Isolation & sandbox**
- **Local OS sandbox**: Seatbelt (macOS), bubblewrap+seccomp (Linux/WSL2), egress via HTTP/SOCKS allowlist proxy. Modes: `per-command` (default) and `whole-process` (**refuses to start** rather than run unsandboxed). Defaults: reads all, writes CWD-only, denyWrite overrides allowWrite; network deny-all except Factory/WorkOS (autonomy-and-safety/sandbox).
- **Git worktrees as fan-out primitive**: `droid exec -w <name>` runs in a worktree on its own branch; clean auto-removed on exit, dirty preserved — DevAgent's per-run worktree pattern as a first-class CLI flag.
- **Droid Computers**: persistent compute (managed: 4 CPU/8 GB/6 GB swap, `factory-user` w/ passwordless sudo, auto-pause/resume) or **BYOM** (`droid computer register`). Access via WebSocket tunnel + Factory-managed Ed25519 keys (no inbound ports); org-level **relay mode** = infrastructure-level network boundary; iptables lockdown otherwise; per-user git creds auto-injected on managed computers (droid-computers/overview).
- **Enterprise deployment**: cloud-managed / hybrid / **fully airgapped** (on-prem models, in-network OTEL, offline artifact import — "default pattern for national security, defense, and highly classified workloads"); proxy/custom-CA/mTLS; Enterprise audit log (actor/source/target/payload, managed-settings revision tracking); on-prem, sub-orgs, CMEK, data residency (pricing/organizations).

**Validation & self-repair loop**
- Milestone validation workers + QA skill + review gate; **failure learning feeds back into the QA skill**: new failure patterns can auto-commit sub-skill updates or open a draft PR updating the failure catalog (`failure_learning: suggest_in_report | auto_commit | open_pr`) (automated-qa).
- **Agent Readiness levels 1–5** (Functional→…→**Autonomous**), gated at 80% of the prior level, scored on 9 pillars, evaluated per repo and per app in monorepos; `/readiness-fix` auto-remediates; **Missions require Level 4+** (agent-readiness/overview, missions/overview).
- Factory Router + BYOK: `customModels` entries (baseUrl/provider/maxOutputTokens) referenced as `custom:<name>-<idx>` (droid-exec/overview).

**Human gates & approval UX**: ExitSpecMode plan approval; per-action approval by autonomy level; hook `permissionDecision: allow|deny|ask`; org `missionPolicy` allowlist for mission launches; org-managed hooks with `allowManagedHooksOnly`; Enterprise audit log.

**Cost model / metering mechanics**
- Three independent rolling rate limits: **5-hour, 7-day, 30-day** — need headroom in all three. "Standard Usage" first, then **Droid Core** (free open-weight pool, separate limits) keeps runs alive; prepaid **Extra Usage** ($10 min, no expiry) as overflow. **Missions require Extra Usage and pause on rate limit** (pricing/individuals). Teams = per-seat Pro limits; Business/Enterprise = contract custom limits; Enterprise adds partitioned inference (pricing/organizations). Community complaints about weekly limits persist (r/FactoryAi, forum-only).
- Agent Effectiveness + OTEL export + Analytics API: token/cost estimates via API only (not OTEL), productivity correlated to touched issues/PRs (agent-effectiveness/cost-and-productivity).

**What DevAgent can steal**
1. **Two named validation worker roles per milestone** (scrutiny vs user-testing) with separate models — template for splitting DevAgent validation into a cheap reviewer model + expensive user-flow model, with published cost math.
2. **Exit-code-as-gate + `--auto` risk tiers** (Off/Low/Medium/High, org-capped) for headless worker invocations.
3. **OS sandbox ladder** with "refuse to start rather than run unsandboxed" — closes backlog idea #1 (2026-09-07 synthesis); denyWrite-overrides-allowWrite is the `.git`-write-protection pattern.
4. **Repo-local review-guidelines file** auto-injected into review runs — G4 prompts should load per-repo guideline files.
5. **Self-updating failure catalogs** (`auto_commit`/`open_pr`) — lessons digest is per-run; commit new gate fixtures from observed failures instead.
6. **Agent Readiness scoring as intake gate** + `/readiness-fix` remediation PR, computable from DevAgent ledger evidence.
7. **The 8-clause "is it a bug" rubric** pasted into G4 prompts to suppress style noise.

**Hook surface (gate enforcement)**: `hooks.json` keyed by event (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PreCompact`, `SessionStart/End`) with tool matchers incl. `mcp__.*` and `commandRegex`; exit 2 = block + stderr fed back; JSON supports `permissionDecision` (allow/deny/ask), `updatedInput` (rewrite tool args pre-exec), `additionalContext`, and Stop-blocking (`decision: block` + reason = force continuation). Org hooks always load; `allowManagedHooksOnly: true` strips user/project hooks — the reference implementation for DevAgent's named-hook lifecycle idea (harness/hooks).

## Cursor — Cloud Agents, Bugbot, Automations, Origin

**What it is / status (2026-09)**: Background Agents renamed **Cloud Agents**; 2026 expansion: Automations framework; three Cursor-managed review agents (Bugbot, Security Agents, **PR Routing & Approval**); first-party "Cursor Models" (Grok 4.6/4.5 "jointly trained by Cursor and SpaceXAI" [single source, pricing table — treat name cautiously], Composer 2.5); **Origin**, a first-party git forge in early beta (repos, PRs, review/merge, Origin Apps, agent-created repos) (docs/origin.md).

**Trigger surfaces**: iOS app, web (`cursor.com/agents`), desktop, Slack `@cursor`, GitHub/Bitbucket/Azure DevOps/PR+issue comments, Linear, **Sentry** and **PagerDuty** triggers, **webhooks**, cron schedules; `cursor.com/automations` + marketplace templates + `/automate` skill converting plain language to trigger+prompt+tools (cloud-agent.md, cloud-agent/automations.md).

**Workflow pipeline (stage by stage)**
1. **Trigger** → Cloud Agent in an isolated cloud VM on a separate branch (repo cloned server-side; multi-repo environments supported, long-running not yet) (cloud-agent.md).
2. **Environment prep** (the doc's own #1 lever): `.cursor/environment.json` (agent-led setup, saved snapshot, or Dockerfile); **Builds** prepare environments in the background so agents start with deps ready; dashboard shows which build each run used (cloud-agent.md, cloud-agent/builds.md).
3. **Execute** with MCP (HTTP+stdio, OAuth), computer use, team hooks from `.cursor/hooks.json`.
4. **PR + artifacts**: "merge-ready PRs" plus screenshots/videos/logs of how the agent verified its work, and **remote desktop control** — you take over the agent's VM desktop to test, then release it back (cloud-agent.md).
5. **Review loop**: Bugbot reviews every PR update (or `cursor review`/`bugbot run` comment), reads existing PR comments as context; **incremental reviews** (diff since last review) by default; publishes a `Cursor Bugbot` check that defaults to `neutral` on findings (`failure` only with fail-on-unresolved enabled) (bugbot.md).
6. **Autofix**: Bugbot spawns a Cloud Agent to fix findings, pushing to a new branch (recommended) or the existing branch with a **max 3 attempts per PR cap "to prevent loops"** — an explicit retry bound on the reviewer→worker repair loop (bugbot.md).
7. **Approval gate**: PR Routing & Approval assigns reviewers by ownership+history, risk-scores PRs, auto-approves low-risk ones. File-based enforcement: per-directory `APPROVAL_POLICY.md` (exact basename only), `.cursor/approval-policies/ROUTING.md` for product boundaries, Bugbot/Security findings as approval signals; **if the PR modifies an approval policy or routing file, the agent uses the base-branch version, never the PR's own relaxation** (approval-agents.md).

**Isolation & sandbox**: per-agent isolated VM (Cursor manages provisioning/snapshots/capacity); three secret classes — Env Var (visible), **Runtime Secret** (loaded but redacted as `[REDACTED]` in tool results, transcripts, commits), **Build Secret** (Docker build-only via secret mounts); OIDC identity tokens; signed commits; egress allow-all / default+allowlist / allowlist-only; published egress IP ranges + **git egress proxy**; private networking via Tailscale / Cloudflare Tunnel; Enterprise PrivateLink (SCM, Artifactory/Nexus); Protected Git Scopes. **Self-hosted machines**: tool execution on your own hardware, worker pools. Cloud hooks run from repo `.cursor/hooks.json` (`preToolUse`, `beforeShellExecution`, `afterFileEdit`, `beforeSubmitPrompt`, `subagentStart/Stop`, `preCompact`, `stop`); no user-level hooks; hooks don't fire during early read-only exploration.

**Validation & self-repair loop**: Bugbot effort levels Low/Default/High/**Smart** (describe when to spend more); **learned rules** mined from team GitHub activity or backfilled from repo history; `@cursor remember [fact]` inline rule creation; scoped-path rules; rule analytics; rules include repo-specific enforcement like "require tests for backend changes" (bugbot.md).

**Human gates & approval UX**: spend limit at first Cloud Agent use; approval-policy files; risk threshold; admin Bugbot repo enable/disable via API; team follow-ups toggle.

**Cost model / metering mechanics**
- Two usage pools: **Cursor Models** (first-party Grok/Composer, generous included usage, exempt from token rate) vs **Other Models** (third-party at API price). Plans Pro $20 / Pro Plus $60 / Ultra $200 / Teams $40–$120 per seat (Premium = 5× Standard agent limits) / Enterprise custom (pooled usage); **Start (India only) ₹649/mo** (models-and-pricing.md).
- **Cursor Token Rate $0.25/Mtok on all third-party model traffic** on Teams/Enterprise — on top of API price, including BYOK — a platform tax steering teams to first-party models. Auto modes (Cost/Balance/Intelligence) bill at the routed model's list price; on-demand usage billed monthly at API rates.
- Cloud Agents billed at model API pricing with user-set spend limits; **Automations always use max context window (no toggle)** — silent cost multiplier.
- **Quota-exhaustion evidence**: Bugbot moved from $40 flat to usage-based in **May 2026** (cursor.com/blog/may-2026-bugbot-changes); forum: **~$30 per Bugbot run (38.3M tokens), $300 in 2 days** on a large monorepo (…164241, 2026-06-28); "the new usage-based Bugbot pricing punishes iterative workflows and power users" (…161134, 2026-05-20); Sept-2025 usage-based pricing backlash (…135489). Effort levels gated behind usage-based billing tier.

**What DevAgent can steal**
1. **APPROVAL_POLICY.md per-directory merge-gate contract** + anti-self-relaxation rule (base-branch policy version when the PR touches the policy).
2. **Runtime Secret redaction** (`[REDACTED]` in tool results/transcripts/commits) — implementable in worker spawn env + transcript writer.
3. **Autofix attempt cap (max 3/PR)** as a documented, visible retry bound per PR.
4. **Environment "Builds"** (pre-baked snapshot + Dockerfile, prepared in background, run-visible) — pre-pull/build Compose images before dispatch; stamp each ledger row with the environment build ID.
5. **Bugbot check semantics**: findings = `neutral` by default, `failure` opt-in — distinguishes "found issues" from "gate failed" so branch protection isn't accidentally bypass-blocking.
6. **`@cursor remember` inline learned rules** — one-line path from review feedback into durable repo rules; lessons file could accept PR-comment-encoded lessons.

## AWS — Amazon Q Developer, AWS Transform, Kiro

**What it is / status (2026-09)**: AWS's agentic-coding story re-partitioned. (a) **Amazon Q Developer IDE plugins hit end of support 2027-04-30**, Kiro named successor ("explore Kiro to access the latest models and features, including agentic coding, chat and MCP support"); the old `/dev` agentic feature-dev docs are gone from the Q doc set. (b) **Q Developer for GitHub** (preview) is the surviving autonomous issue→PR agent. (c) **Code transformation is now a standalone product, "AWS Transform"** (docs.aws.amazon.com/transform — Java, .NET, mainframe, VMware, containers), absorbing Q's `/transform`. (d) **Kiro** is the spec-driven IDE/CLI/Web/Mobile agent with cloud sandboxes and autonomous mode.

### Q Developer for GitHub (preview) — issue→PR agent

**Pipeline**: 1. issue label `Amazon Q development agent` (app auto-creates it; exact name required) or `/q dev` comment → 2. Q uses issue title/description + repo as context, implements → 3. comments on the issue with the PR link → 4. iteration: human line comments or `/q implement my suggestions` → Q replies with a change plan, then commits → 5. human merges. Monthly free usage cap; registering the installation with an AWS account raises limits.
**Review loop**: auto code review on PR create/reopen + `/q review` on demand; threaded findings; Q **generates fixes**; cap measured in *lines reviewed per month*; console-level toggle (github-code-reviews.html).

### AWS Transform — job-orchestrated migration agent

**Pipeline** (.NET web app; Java analogous): 1. connect source control (Azure Repos/Bitbucket/GitHub/GitLab) or S3 zip → 2. **Assessment** report + missing-dependency resolution (upload NuGets) → 3. **global modernization plan** review: repository topology in **waves** (dependency-ordered), Feature & Package Migration Map (before/after packages), strategy with risks/mitigations; plan is editable markdown, discussable in chat, replaceable by an **uploaded steering document** (org conventions, package preferences) → 4. **Transform**: repositories transformed **in parallel batches**; progress via dashboard/chat/transform panel/**Worklog tab** (natural-language agent activity); **per-repository checkpoint toggles** pause the batch for human review (download, discuss, refine, or **full retry with revised instructions**) → 5. output: new writable branch per repo (or S3 zip), artifact download, or **"beaming" repos to developers** in the final summary; validation = **local builds + unit test porting** (dotnet.html, dotnet-web-review-and-customize-plan.html, dotnet-web-transform-code.html).
**Java path**: plan generated from a local build artifact; transform server-side in steps; **after each step, code goes back to your local environment for verification builds + existing unit tests** (private-resource access), then continues server-side; 30-day artifact retention; summary shows plan-vs-actual diff + build log; explicit human gates: connector setup, plan validation, missing packages, accept changes (how-CT-works.html).
**Continuous modernization (fleet layer)**: connect orgs → discover repos (labels for team/priority/wave) → scheduled analyses (rapid tech-debt metadata scan, comprehensive code-level debt, security via AWS Security Agent, **agentic-readiness scored on 56 criteria across 5 categories**, modernization-readiness, custom) → findings triage (severity, dismiss-with-reason, auto-obsolete on re-analysis) → **autonomous remediation opening PRs/MRs at scale** driven by **transformation definitions** (`atx custom def list`) → `atx ct schedule` (EventBridge Scheduler). Compute: local (default), AWS-managed (analysis-only), AWS Batch/Fargate (one isolated container per analysis, recommended), or EC2 — all in the customer's account (continuous-modernization.html).

### Kiro — spec-driven delivery with property-based correctness

**Trigger surfaces**: IDE/CLI interactive; **Web/Mobile cloud sessions** (scheduled automations, web-only); GitHub `kiro` issue label or `/kiro` comment (Kiro Agent GitHub App); CLI headless; ACP support.
**Workflow pipeline (autonomous mode, app.kiro.dev)**: 1. **Clarification** — agent asks questions upfront; 2. **Planning** — decompose, generate requirements, define acceptance criteria; 3. **Execution** — specialized **sub-agents per step**, "analyzing the codebase, writing code, and verifying changes before moving forward"; model chosen automatically; 4. **Completion** — opens one or more PRs with changes/approach/trade-offs (docs/web/autonomous-mode). GitHub loop: per-task isolated sandbox, feature branch from default, **co-authored commits (you + agent)**, PR authored by the Kiro app or (toggle) as your own GitHub identity for branch-protection/CI compatibility; then **PR-comment repair**: `/kiro all` (all reviewers, whole PR) / `/kiro fix` (one thread); **GitHub Action feedback is automatically addressed on any user feedback**; in-session Reviews panel; learning restricted to the task owner's comments (docs/web/github).
**Spec gates (feature specs)**: two variants — Requirements-First (requirements→design→tasks) and **Design-First** (design→requirements→tasks); `requirements.md` in **EARS notation** ("WHEN … THE SYSTEM SHALL …") for testable/traceable requirements; explicit **Analyze Requirements** pass for inconsistencies/ambiguities/conflicting constraints/gaps before design; per-phase approval gates, or **Quick Spec** which runs all three phases unattended after upfront clarifying questions (docs/specs/feature-specs/).
**Property-based correctness gate (sharpest AWS validation mechanism)**: **Spec correctness** extracts **properties** from EARS requirements, decides which are logically testable, generates PBT cases during design, runs them against the implementation at task-execution time (optional by default), and on failure surfaces the **shrunk counter-example** for a chat-driven decision: fix impl / fix test / **refine the requirement**. IDE-only today; docs explicitly frame it as evidence, not proof (docs/specs/correctness/).
**Hooks**: `.kiro/hooks/<id>.json` — triggers Prompt Submit (can block), Agent Stop, Session Start (IDE) / Agent Spawn (CLI), **Pre Tool Use (can block)**, Post Tool Use, File Create/Save/Delete (**agent-made changes only** — manual editor saves don't fire), **Pre/Post Task Execution** (spec-task lifecycle); matcher = regex over tool categories (`read/write/shell/web/spec`, `@mcp`, `@powers`, `*`); actions = shell command (JSON on stdin; exit 0 → stdout into agent context, else stderr warning) or **agent action** (inject a prompt into the conversation) (docs/hooks, docs/hooks/types).
**Steering**: `.kiro/steering/*.md` with inclusion modes always/fileMatch/manual, workspace-over-global precedence, AGENTS.md support, generated foundation files (product.md etc.), team steering via MDM/GPO (docs/steering).
**Isolation**: cloud sessions run the same harness in **sandbox-backed** compute, **up to 10 concurrent**, **no separate compute charge**; repos cloned server-side ("your local working copy is never uploaded"); session store decoupled from clients — attach/detach keeps the agent running and **approvals queue until the next client attaches**; per-task sandbox: spin up → clone authorized repos → configure from detected project settings → execute with only explicitly permitted resources → **tear down**; every sandbox ships **headless Chrome + Playwright MCP + agent-browser CLI + Chrome DevTools MCP** for UI self-validation; per-task domain allowlist (docs/cloud-sessions, docs/web/sandbox).
**Enterprise**: IAM Identity Center/Okta/Entra; model governance, **MCP governance/allowlist**, permission governance, prompt logging, OpenTelemetry user-activity export, managed updates (docs/enterprise/*).
**Pricing mechanics** (tiers unchanged vs 2026-09-07): "a credit is a unit of work in response to user prompts"; simple prompts <1 credit; **spec-task execution typically >1 credit**; model-dependent rates (Sonnet 4.6 > Auto); **agent hook execution consumes credits**; `Auto` = routing agent mixing frontier + specialized models with intent detection and caching; add-on $0.04/credit (12-month expiry); Enterprise overages opt-in (kiro.dev/pricing).

**What DevAgent can steal**
1. **Property-based tests derived from acceptance criteria** — DevAgent tickets already carry structured criteria; deriving invariants and running Hypothesis against the diff attacks the same "does impl match spec" question G1 answers only example-wise. Nobody else in this set ships it.
2. **EARS-notation ticket format** as the plan contract (each `WHEN…SHALL` maps to a test) — makes G1's FAIL_TO_PASS list mechanically derivable.
3. **Step-wise hybrid verification** (transform server-side, verify locally after *each* step) instead of validate-at-the-end — natural fit for migration tickets given DevAgent is already local-first.
4. **File-trigger scope rule**: gate hooks fire only on agent-made changes, ignoring operator edits (avoids self-triggered storms).
5. **Approval queueing across disconnects** — pending approvals live in the ledger, not in a pane, so a dead TUI never strands a run.
6. **Findings→auto-remediation-PR fleet loop** with transformation definitions as reusable fix knowledge (= DevAgent lessons, but per-finding and repo-targeted); `agentic-readiness` 56 criteria as a second readiness-score reference.

## Sourcegraph Amp

**What it is / status (2026-09)**: Terminal/web/iOS/CLI coding agent (Sourcegraph spun it toward an agent product; docs lastModified 2026-08-27→09-10). The distinguishing bet: **Orbs** — remote machines where agents work, treated as durable, resumable, *purchasable compute* — plus aggressive model routing ("The Dial") and an agent-to-agent delegation protocol.

**Trigger surfaces**: web threads, CLI (`amp -ox` spawns an orb thread; `--orb-size`), TUI palette, macOS/iOS apps, **scheduled automations in natural language**, **plugin-created webhooks** (`amp.createWebhook({key, headers, handler})` returns a public POST URL), Slack DMs via personal **Puck**, SDK (TS/Python).

**Workflow pipeline (stage by stage)**
1. **Thread/orb start**: fresh isolated environment with your code, plugins, dev tools, and the creating thread's context.
2. **Spawn pacing as a fairness mechanism**: burst of 20 metered orbs per user, then **one new orb every five minutes**; later starts *queue with an estimated wait* rather than fail.
3. **Execute**: agent installs deps, runs your app, spawns browsers — "tell it to prove that its changes work before you look at them"; **Terminal pane shares the same tmux session/filesystem** so a human runs alongside; `amp sync <thread>` mirrors orb changes into your local checkout *while the agent keeps working*.
4. **Idle economics**: orb auto-pauses after 5 minutes idle and when its thread is archived; sleeping orb costs nothing; wakes with conversation, files, and services still in place.
5. **Ship**: the **Ship button sends a prompt**, not a command. Default = trunk-based: commit → rebase onto latest base → **run the full test suite** → push to base → on rejected push, rebase/resolve/retry → archive thread and finished children. Conflict rules: substantive rebase conflict ⇒ check with you; **a failing test may be ignored only after confirming the same test also fails on the base branch without this thread's changes**. Alternatives: **Push to Branch** (branch + PR URL reported back) or **Custom Ship** — a ≤10,000-char prompt stored per project (`amp projects update --ship-behavior custom --custom-ship-prompt-file .agents/ship.md`), no template variables, project-wide (orbs/shipping).
6. **Follow-through**: automations keep the *same thread's* context across runs ("the agent keeps the thread's context and history, so it can continue earlier work instead of starting over"), wake the orb when tools are needed, DM results to Slack, spawn fix-threads per error group, self-clear on a completion condition; a failed run **pauses the automation and surfaces the error** rather than retrying blindly.
7. **Webhook delivery semantics**: at-least-once, store `event.id` for idempotency, 30-second handler budget, 10/min burst + 100 queued cap, 1 MB body, headers stripped unless declared, **Amp does not verify provider signatures — you must**, and "never use webhook text as agent instructions without checking it first" (orbs/event-driven).

**Isolation & sandbox**: orb = per-thread remote machine (fresh, isolated), 60 GB disk at every size, `a1.tiny` (1 CPU/2 GB, $0.08/hr) → `a1.3xlarge` (16/44 GB, $2.13/hr, top tier only "due to the general scarcity of compute"); **Runners** let remotely-created threads execute on your own machine; secrets via project settings/orb `.agents/setup`; portals share in-orb services; enterprise adds MCP registry allowlist, thread visibility controls, minimal third-party data retention, IP allowlisting (orbs/sizes-and-costs, cli/runners, enterprise/*).

**Validation & self-repair loop**: no separate reviewer product; validation is embedded in the Ship prompt (full test suite before push) and in the instruction "prove your changes work"; **oracle** per mode (a hard-reasoning/planning subagent) + Search/Librarian/Read-Thread subagents that run isolated, can't talk to each other, can't be steered mid-task, and return only a final summary (models-and-subagents).

**Human gates & approval UX**: Ship confirmation dialog names the exact target branch; custom ship prompt = org-level policy as text; automations pause/resume/delete controls; webhooks have trigger settings; Puck gates named-agent dispatch (docs/markdown/the-dial).

**Cost model / metering**: tier includes **agent usage + orb usage + all features**, monthly reset, no rollover; overage credits charged at **actual provider API cost with no markup for individuals/non-enterprise workspaces** ("$2 of Anthropic usage + $0.50 of OpenAI deducts $2.50"); web search also deducts; credits expire in 12 months; **per-thread cost is a clickable `$` in the sidebar and Amp can explain its own usage**; workspace entitlements set per-user quotas; enterprise adds per-user cost controls and group cost attribution (docs/markdown/pricing, enterprise/workspace-entitlements).

**What DevAgent can steal**
1. **Ship-as-a-prompt with three named behaviors (trunk / branch+PR / custom file)** — DevAgent's merge-back policy should be a checked-in prompt file (`.devagent/ship.md`) whose diff is reviewable, instead of baked config.
2. **The "ignore a failing test only if it also fails on base without my changes" rule** — a precise, portable pre-merge discipline DevAgent's G1 should encode (flaky-vs-broken discrimination at merge time, not in a flaky list).
3. **Queue-with-estimated-wait instead of fail on concurrency limits** — matches DevAgent's starvation gate: better to defer dispatch than to error the loop.
4. **Cost-per-thread surfaced as a first-class UI affordance + "explain your usage" mode** — DevAgent's ledger has the data; nobody in the enterprise cluster lets you interrogate the invoice except Amp.
5. **Webhook hardening checklist** (at-least-once + event-id dedupe + 30 s budget + signature-not-verified disclosure + untrusted-payload warning) — directly reusable for DevAgent's incoming-triggers surface.
6. **`amp sync`** — mirror a remote run's changes into a local checkout without stopping the worker: high-value for DevAgent's TUI attach/detach story.

## Cluster synthesis

- **Everyone converged on the same seven stages; differentiation moved to *where the gates live*.** Triage → spec/plan (approval-gated) → execute in isolated worktree/VM → validate → PR → comment-driven repair → (now) release/document/monitor. Factory's Software Factory and Kiro's Automations show 2026's expansion is *horizon-wide* (SDLC coverage maps, incident response, docs refresh), not deeper into codegen. "Ticket→PR" is the industry baseline now — DevAgent's differentiator has to stay validation depth + evidence + local-first/BYO.
- **The most important mechanism in this cluster is repo-local policy as files**: `APPROVAL_POLICY.md` (Cursor), `.factory/skills/review-guidelines/SKILL.md`, `.factory/droids/*.md`, `.kiro/hooks/*.json`, `.kiro/steering/*.md`, `.cursor/environment.json`, Amp's `.agents/ship.md`. Policy is reviewable, diffable, and org-overridable (`allowManagedHooksOnly`, `maxAutonomyLevel`, workspace entitlements). DevAgent's gates are program-config today; making the *contract per repo* a checked-in artifact is the pattern all four adopted this cycle.
- **Retry policy is converging on small explicit numeric caps**, published in docs: Cursor Autofix 3 attempts/PR, Factory mission per-feature retry warning + "mark complete and move on" operator escape hatch, Amp one-orb-per-5-min queue and pause-on-failed-automation, Kiro "full retry with revised instructions" at a checkpoint. DevAgent's breaker/starvation limits are the same species — the steal is *advertising* them (per-PR attempt budget in the PR body, automation-pause reason) rather than leaving them in the ledger.
- **Validation depth is narrowing from the low end**: Kiro's EARS→property→PBT gate, Cursor's "require tests for backend changes" rules, Amp's full-suite-before-push, and Q's step-wise local verification builds move "did it work" out of the CI-only layer. DevAgent's uncontested ground remains **domain-shaped backend gates** — migration safety (Squawk/Atlas + shadow-DB replay), FK integrity, async/race review, threat-model gates; none of the four has anything schema-aware, and the strongest new entrant (Kiro PBT) is IDE-only and optional-by-default. Steal-and-extend: add PBT-derived invariant checks, and name the migration gate as a visible PR check (competitors brand theirs: "Cursor Bugbot", "Security Review").
- **Surprise / moat-sharpening**: two of the four (Cursor, Kiro) now have a *pricing-driven exit population* (third-party token tax; credits burned by hooks and task execution), and Factory self-serve still trips rolling limits below Enterprise (PRD §19.2's "quota risk below Enterprise" holds). That is DevAgent's wedge: local, BYO-model, ceiling = your own API key, plus backend-domain gates none of them ship. Threat side: Factory Software Factory and Kiro autonomous Web already do ticket→PR→comment-repair with enterprise controls DevAgent lacks (audit log, airgap, MCP governance), and Cursor's **Origin** forge suggests platforms may absorb the git host — DevAgent's git-agnostic BYO-repo design becomes the counter-argument, not the weakness.
