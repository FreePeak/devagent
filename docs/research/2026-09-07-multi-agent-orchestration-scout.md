# Research: Multi-agent orchestration patterns for DevAgent's orchestrator, fleet, and merge queue

Date: 2026-09-07
Scope: Coordination, failure/retry/lease, budget, and human-in-loop patterns from production multi-agent systems and merge-queue tooling, mapped to concrete adoptable ideas for DevAgent (src/orchestrator/, fleet panes, merge-back, gates). All external claims cite fetched URLs; local file references verified in-repo.

## Orientation: what DevAgent has today

`src/orchestrator/` contains: `planner.ts` (LLM decomposition of a goal into 2-6 tasks with `dependsOn[]`), `scheduler.ts` (waves, concurrency, maxTaskRetries/maxRecoveries/maxWaves), `governor.ts` (`ResourceGovernor` sizing the worker pool from live OS signals: mem-cap = free*safetyRatio/estPerWorker with p75 RSS self-calibration, cpu cap, `auto` mode), `merge.ts` (topological merge-back in dependency order, `git merge --no-ff` per branch, re-runs the test gate on the integrated tree after every merge, rolls back the failing merge; `perTaskPrPublished()` disables legacy merge-back when PRs exist), `queue-bridge.ts`, `ledger.ts`, `auditor.ts`, `board-recovery.ts`, `selfbuild-gate.ts`, `pr-hygiene.ts`.

Three orchestration surfaces coexist (docs/ORCHESTRATOR-FACTORY.md): the queue/factory model (scout picks one backlog item, builder consumes), the DAG/board model (planner + scheduler + auditor), and War Room (docs/WAR-ROOM.md: research → spec-critique loop → AC checklist implementation, with circuit breaker + starvation gate + `WARMROOM_MAX_CONSECUTIVE_FAILURES=3`, conservative judge requiring cited evidence per criterion). docs/MERGE-QUEUE.md tracks a manually-curated ordered stack of PRs with `git merge-tree` conflict verification — i.e., the merge queue today is a human/loop-maintained document, not code.

## Coordination patterns

### Orchestrator-worker (Anthropic Research)

Anthropic's Research feature uses a lead agent that plans, spawns specialized subagents operating in parallel with their own context windows, then compiles results (https://www.anthropic.com/engineering/built-multi-agent-research-system). Key numbers: multi-agent with Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on their internal research eval; token usage alone explains 80% of BrowseComp variance (three factors explain 95%); agents use ~4× chat tokens, multi-agent systems ~15×. Failure modes they hit: spawning 50 subagents for simple queries, endless searching for nonexistent sources, agents distracting each other with updates. Fixes: explicit effort-scaling rules in prompts ("simple fact-finding = 1 agent with 3-10 tool calls; comparisons = 2-4 subagents with 10-15 calls; complex = 10+ subagents with divided responsibilities"), detailed delegation templates (objective, output format, tool guidance, task boundaries), parallel tool calls (3-5 subagents in parallel; 3+ tools per subagent), and writing subagent outputs to a filesystem artifact rather than passing everything through the lead — "to minimize the game of telephone". They also stress durable execution (agents are stateful; errors compound; restart-from-scratch is expensive) and end-state evaluation for agents that mutate state.

### Counterpoint: single-threaded linear agent (Cognition)

Cognition's "Don't Build Multi-Agents" (https://cognition.com/blog/dont-build-multi-agents, Walden Yan, 2025-06-12) argues two principles: (1) *share context, and share full agent traces, not just individual messages*; (2) *actions carry implicit decisions, and conflicting decisions carry bad results* — the Flappy-Bird example: two subagents each misinterpret nuance and the combiner inherits both miscommunications. Default prescription: a single-threaded linear agent with continuous context; when context overflows, add a dedicated context-compressor LLM that condenses history into key decisions ("hard to get right", possible fine-tune target). They note Claude Code (as of June 2025) deliberately never runs subtask agents in parallel with the main agent — subagents answer well-defined questions rather than write code — precisely because the subagent lacks the main agent's context. On parallelism, they observe agents can't yet do the human protocol of talking out conflicting assumptions, so parallel coding agents are risky when their actions interact.

**DevAgent reconciliation.** DevAgent already runs the pattern both posts debate: planner → independent workers in worktrees → auditor/merger. Cognition's principles justify DevAgent's existing *serialization defaults* (topological merge order, one-item-per-iteration selfbuild loop) and give a concrete gate: before the scheduler widens a wave beyond one worker per file-region, require evidence the tasks touch disjoint surfaces (the board's `dependsOn` plus a file-scope annotation) — otherwise fall back to sequential dispatch. Anthropic's filesystem-artifact pattern is already half-present (worktrees + ledger); the gap is that worker *findings* flow back as summarized streams, not inspectable artifacts.

### Supervisor / hierarchical patterns (LangGraph, AG2, crewAI)

- LangGraph models workflows as state graphs; nodes do work, edges route, reducers merge updates (https://docs.langchain.com/oss/python/langgraph/graph-api). The supervisor library implements hierarchical delegation via tool-based handoffs, with the team lead controlling all communication; LangChain now recommends the supervisor pattern "directly via tools" for control over context engineering (https://github.com/langchain-ai/langgraph-supervisor).
- AG2 (ex-AutoGen) ships built-in conversation patterns — two-agent chat, Group Chat, Swarm — plus a first-class `ag2/a2a/` module (cards, tasks, transports: jsonrpc/grpc/rest) exposing agents over A2A (https://github.com/ag2ai/ag2, https://docs.ag2.ai/latest/).
- crewAI crews run `sequential` or `hierarchical` (manager LLM/agent required for hierarchical) with per-crew `max_rpm` rate limiting, crew-level `token_usage` in output, `planning` pre-pass (AgentPlanner rewrites task descriptions), and memory/cache knobs (https://docs.crewai.com/v1.15.20/en/concepts/crews).

## Failure, retry, timeout, and lease patterns

**LangGraph fault tolerance** (https://docs.langchain.com/oss/python/langgraph/fault-tolerance): three composable per-node mechanisms — `RetryPolicy` (max_attempts=3 default, exponential backoff with jitter, `retry_on` classifier that by default retries only transient errors: 5xx from http libs, timeouts; never ValueError/TypeError/SyntaxError-class), `TimeoutPolicy` (incl. `idle_timeout` for hung nodes, overridable per-`Send` in map-reduce fan-out), and an `error_handler` that runs only after retries are exhausted and can rewrite state and re-route. Composition order is fixed: timeout → retry classifier → handler. There is also graceful shutdown at superstep boundaries.

**Persistence/checkpointing** (https://docs.langchain.com/oss/python/langgraph/persistence): checkpointers persist thread-scoped graph state for resume-after-failure, human-in-the-loop, and time travel; stores hold cross-thread long-term memory; troubleshooting notes call out unbounded checkpoint growth (prune/retention policy) and that in-memory savers die on restart — production needs Postgres/SQLite savers.

**crewAI checkpointing** (https://docs.crewai.com/v1.15.20/en/concepts/crews): `checkpoint=True` or `CheckpointConfig(location, on_events=["task_completed"], max_checkpoints=5)` with `Crew.from_checkpoint()` resume — bounded retention by default.

**MCP Tasks (2025-11-25 revision, experimental)** (https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks, changelog https://modelcontextprotocol.io/specification/2025-11-25/changelog): task-augmented requests turn any tool call into a durable state machine — receiver returns `CreateTaskResult` with `taskId`, `status`, `ttl`, `pollInterval`; requestor polls `tasks/get` until terminal (`completed|failed|cancelled`) or `input_required`, then fetches via `tasks/result`; capability negotiation (`tasks.requests.tools.call`, tool-level `execution.taskSupport: required|optional|forbidden`) plus `tasks/cancel` and status notifications. The same revision adds sampling tool-calling (`tools`/`toolChoice`), OIDC-discovery auth, OAuth Client ID Metadata Documents, elicitation enum/URL-mode updates, and registry-aligned `server.json` metadata. This is the closest thing to a standard lease/poll protocol for long-running agent work.

**Managed Agents: brain/hands/session separation** (https://www.anthropic.com/engineering/managed-agents, 2026-04-08): don't adopt a pet — the sandbox is cattle, provisioned via `execute(name, input) → string` tool calls; the harness is cattle too, rebooted with `wake(sessionId)` and resumed from the last event in the durable, append-only session log (`getEvents()`), which lives *outside* the model's context window so context management (slicing, cache-friendly transformation) is reversible. Results: p50 time-to-first-token dropped ~60% once containers were provisioned lazily. Auth never enters the sandbox (repo tokens wired into git remotes at init; OAuth held in a vault).

**Claude Code hooks** (https://code.claude.com/docs/en/hooks): deterministic lifecycle gates — `PreToolUse` can deny a tool call (e.g. block `rm -rf`) via JSON decision on stdout; `PermissionRequest`/`PermissionDenied` (with `retry: true` re-permit) implement human/auto approval; `SubagentStart/Stop`, `TaskCreated/Completed`, `Stop/StopFailure`, `Pre/PostCompact`, `WorktreeCreate/Remove` cover spawn/finish/compaction/worktree events. Hooks compose across settings levels and run inside subagents. This is an existence proof that gate logic can live entirely outside the model.

## Merge-queue patterns

**GitHub merge queue** (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue and https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue): FIFO queue on a protected branch; each entry gets a temporary `gh-readonly-queue/{base}` branch containing base + all ahead-of-it entries; CI runs on the `merge_group` event; on pass, entries merge together; on one entry's failure it is removed and the group is rebuilt without it. Knobs: build concurrency (1-100 concurrent merge-group CI builds), status-check timeout, merge limits (min/max group size + wait-timeout for the minimum), and "only merge non-failing pull requests" (off = optimistically batch a failing PR as long as the *last* one passes, tolerating intermittent failures). Queue-jumping is supported but forces a full rebuild of in-flight entries.

**bors-ng** (https://raw.githubusercontent.com/bors-ng/bors-ng/master/README.md — note: now deprecated in favor of GitHub's merge queue): the classic batcher. Tests the *combined* batch on a `staging` branch, never pushes a merge to main that wasn't the exact tested tree ("bit-for-bit"); on batch failure it **bisects** the batch into halves and requeues. This is the anti-pattern answer to DevAgent's current merge-back, which merges serially and runs the full suite after *every* merge (src/orchestrator/merge.ts `runTestGate` per branch) — correct but O(n) full-suite runs; batching + bisect gives O(log n) worst case and O(1) typical.

## Budget / token governance

- Anthropic: token spend is the dominant success factor (80% of variance) but multi-agent costs ~15× chat tokens; viability requires task value high enough to pay (https://www.anthropic.com/engineering/built-multi-agent-research-system). Their mitigation is *prompt-encoded effort scaling* — the orchestrator is told, in tokens/tool-calls, how much each task class deserves.
- crewAI: crew-level `max_rpm` (rate-limit governor) and structured `token_usage` surfaced on every output object (https://docs.crewai.com/v1.15.20/en/concepts/crews).
- Claude Code agent teams doc is explicit that teams "add coordination overhead and use significantly more tokens than a single session" and should be reserved for genuinely parallelizable work (https://code.claude.com/docs/en/agent-teams).
- DevAgent already has the hardware half (ResourceGovernor, mem/CPU caps with RSS self-calibration); the *cost* half (tokens per worker × concurrency × wave ceiling) is not connected — crewAI's `token_usage`-on-output and Anthropic's per-class multipliers are the two adoptable halves.

## Human-in-the-loop gates

- Claude Code: `PermissionRequest` hooks + teammate permission prompts surface in the lead session; plan-approval is the designed exception where the lead grants teammate plan approvals (https://code.claude.com/docs/en/agent-teams, /hooks).
- MCP elicitation: `elicitation/create` requests (now with titled/untitled single/multi-select enums, defaults, URL-mode elicitation) give servers a standard way to ask the human mid-task; task-augmented elicitation lets that question be durable/pollable (https://modelcontextprotocol.io/specification/2025-11-25/changelog, /tasks).
- War Room's judge is the local pattern: DONE only with cited per-criterion evidence plus green suite (docs/WAR-ROOM.md) — matches Anthropic's LLM-as-judge with rubric + human eval for edge cases.
- GitHub merge queue treats merge requirements as the human gate: write-access users enqueue, branch protection defines what must pass.

## Protocol surface (A2A + MCP)

A2A (now Linux Foundation; TSC from AWS, Cisco, Google, IBM, Microsoft, Salesforce, SAP, ServiceNow) is agent-to-agent delegation between *opaque* agents: AgentCard discovery, task lifecycle, explicit non-goals (not a sub-agent or tool-call protocol — use your framework's primitives or MCP for intra-system wiring) (https://a2a-protocol.org/latest/). Adoption is broad on paper: the partners page lists 200+ organizations incl. AWS, Atlassian, Bloomberg, Datadog, LangChain, Salesforce, SAP, UiPath, Workday (https://a2a-protocol.org/latest/partners/). MCP remains agent-to-tool; A2A agent-to-agent; they are declared complementary. AG2 already ships an A2A client/server module, showing framework-level integration is cheap (https://github.com/ag2ai/ag2). For DevAgent, MCP Tasks is the higher-value target (gate/delivery contracts); A2A matters only if DevAgent workers must be consumed by third-party orchestrators.

## Concrete adoptable ideas (tagged by DevAgent surface)

1. **[merge] Batched merge queue with bisect** — replace per-branch full-suite gating in `mergeProjectBranches` (src/orchestrator/merge.ts) with bors-style batching: test base+all-done-branches as one integrated tree, merge on pass, bisect halves on failure (https://raw.githubusercontent.com/bors-ng/bors-ng/master/README.md). Directly serves the PRD board-level merged-result oracle; O(log n) instead of O(n) suite runs.
2. **[merge] GitHub merge-group knobs** — adopt the vocabulary and semantics: `status check timeout` (stop waiting on a hung gate), min/max group size + wait timeout, `only-merge-non-failing` toggle for flaky-gate tolerance, and rebuild-without-failed-entry on failure (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
3. **[orchestrator] Effort-scaling ladder in planner prompts** — encode Anthropic's per-complexity budgets (1 worker/3-10 steps → 10+ workers) so the planner stops emitting maximal fan-out for trivial goals; pairs with `maxWaves` as a hard backstop (https://www.anthropic.com/engineering/built-multi-agent-research-system).
4. **[context] Worker findings as filesystem artifacts** — have each worker write a structured `findings.md`/evidence file in its worktree that the auditor reads directly, instead of relying on summarized stream text; Anthropic reports this reduces inter-agent fidelity loss and improves perf (https://www.anthropic.com/engineering/built-multi-agent-research-system). Fits DevAgent's existing worktree-per-worker layout.
5. **[orchestrator] Disjointness gate before parallel dispatch** — Cognition's Principle 2 operationalized: scheduler widens a wave only when board tasks declare disjoint file scopes (extend `parsePlan` validation with an optional `paths[]` field); otherwise serialize (https://cognition.com/blog/dont-build-multi-agents).
6. **[gates] Retry/timeout/error-handler ladder per gate** — port LangGraph's declarative `RetryPolicy`/`TimeoutPolicy`/`error_handler` semantics (retry only transient classes with backoff+jitter, idle-timeout for hung gates, handler after exhaustion) into the G1-G4 gate configs instead of ad-hoc retries scattered in the loop (https://docs.langchain.com/oss/python/langgraph/fault-tolerance).
7. **[gates/product] MCP Tasks for gate exposure** — wrap G1-G4 validation (and the regression oracle) as MCP tools with `execution.taskSupport: required`, returning `CreateTaskResult` with `pollInterval` and `input_required` status for ask-events; any external client (TUI, CI, third party) then gets durable, pollable, cancellable gate results for free (https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks).
8. **[fleet] Cattle sandboxes + session-log resume** — apply Managed Agents' pattern: worker pane death → `wake(sessionId)`-style resume from an append-only session log kept outside the process (ledger + runs/*.jsonl already half-serve this); lazy provisioning of worktrees/panes cuts cold-start dead time, the same lever that cut Anthropic's TTFT ~60% (https://www.anthropic.com/engineering/managed-agents). Maps onto the orphan-pane sweep class: with a durable session log, an orphan is recoverable state, not a loss.
9. **[fleet/gates] Hook-lifecycle for worker panes** — expose DevAgent equivalents of `PreToolUse` deny (block destructive commands in worker shells before they run), `SubagentStop` (evidence check on pane exit), and `PermissionRequest` (route asks to the TUI) so gate logic stays deterministic and outside the model, per the Claude Code hooks model (https://code.claude.com/docs/en/hooks).
10. **[orchestrator] Bounded-resume checkpoints** — crewAI's `CheckpointConfig(on_events=[task_completed], max_checkpoints=5)` + `from_checkpoint()` is a cleaner resume contract than attempt-suffix board mutation: keep the last N board+wave snapshots, resume newest (https://docs.crewai.com/v1.15.20/en/concepts/crews).
11. **[orchestrator/lessons] Token governance wiring** — surface per-worker `token_usage` on every task result (crewAI pattern) and feed Anthropic's ~15× multi-agent multiplier into the ResourceGovernor/wave-ceiling math so budget caps are denominated in tokens×concurrency, not just wall time (https://www.anthropic.com/engineering/built-multi-agent-research-system, https://docs.crewai.com/v1.15.20/en/concepts/crews).
12. **[context/lessons] Context-compressor as first-class component** — Cognition's escalation path when linear context overflows: a dedicated compressor LLM distilling decisions (not just messages) into key facts; DevAgent's lessons digest is the natural home — extend it to compress *worker trace* history per task, not only per iteration (https://cognition.com/blog/dont-build-multi-agents).
13. **[product] A2A AgentCard for external consumption** — only if third-party orchestrators should drive DevAgent workers: an A2A server exposing each worker as an opaque agent with task lifecycle; precedent is AG2's bundled `ag2/a2a/` module (https://a2a-protocol.org/latest/, https://github.com/ag2ai/ag2). Explicitly *not* needed internally — A2A itself disclaims sub-agent wiring.
14. **[product] Merge-queue doc → code** — docs/MERGE-QUEUE.md is a hand-maintained stack table with `git merge-tree` verification; the GitHub/bors patterns show the same semantics (ordered stack, conflict simulation, batch test) belong in `orchestrator/merge.ts` with the ledger recording queue events, retiring the document as the source of truth (https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue).
